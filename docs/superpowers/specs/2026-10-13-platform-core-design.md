## 1. הקשר ומטרה

האפליקציה הקיימת "יומן משימות מוקד" (`index.html`, קובץ אחד, עברית, מתארחת ב-GitHub Pages) משמשת צוות מוקד לניהול משימות והזמנות. נתוני הצוות נשמרים בגיליון Google, ואין בה פרופילי עובדים אמיתיים, תמונות, צ'אט או AI.

מסמך הדרישות של הבעלים (`docs/product/requirements-original-he.md`) מבקש מערכת פנימית לריבוי משתמשים, לאנדרואיד ולמחשב נייד, עם חילוץ נתונים מתמונות באמצעות AI, יומן משימות, צ'אט ודאשבורדים אוטומטיים. זה גדול מכדי לבנות בבת אחת, ולכן הוא מפורק לארבעה חלקים. לכל חלק מסמך עיצוב ותוכנית משלו, וכל חלק נגמר בגרסה שאפשר להתקין.

**מטרת חלק 1:** אפליקציה עובדת, מותקנת על טלפוני אנדרואיד ועל מחשב Windows נייד (ופתוחה גם כאתר), שבה צוות נכנס עם משתמש אישי ומנהל משימות משותפות עם שיוך, עדיפות, תאריך יעד, שדות Glassix / Cargo / איסוף ותמונות. מודל הנתונים כאן כולל כבר את כל מה שחלק 2 (קליטה באמצעות AI) צריך כדי ליצור משימות.

## 3. קריטריוני הצלחה

1. קובץ APK מותקן בטלפון אנדרואיד, מתקין Windows רץ בלפטופ, והאתר נפתח בדפדפן, וכולם עובדים מול אותו פרויקט Supabase.
2. עובד נכנס עם אימייל וסיסמה אישיים. משימה שנוצרה במכשיר אחד מופיעה בכל המכשירים האחרים תוך שניות.
3. כרטיס משימה תומך בשלושת הסוגים עם שדות החובה שלהם, ומזהה שיחת Glassix נאכף.
4. כל שינוי במשימה נרשם בהיסטוריה על שם מי שעשה אותו, ברישום שאי אפשר לזייף מהאפליקציה.
5. מסכי "היום", "משימות" ו"יומן" עובדים בטלפון ובלפטופ, ותזכורות מוצגות כהתראות מקומיות.
6. מנהל יוצר עובדים, עורך סטטוסים והגדרות, מייבא נתונים מהאפליקציה הישנה ומוריד גיבוי.
7. מי שאינו עובד פעיל לא מקבל שום מידע, וסקריפט אבטחה אוטומטי מוכיח זאת.

## 4. הנחות

- צוות של עד כ-20 עובדים, עברית ו-RTL, אזור זמן Asia/Jerusalem, שבוע שמתחיל ביום ראשון.
- הפצה פנימית: APK מותקן ידנית ומתקין Windows. אין חנויות אפליקציות. אין iPhone ואין macOS.
- Supabase בתוכנית החינמית. אומת מול דף המחירים הרשמי ב-2026-10-13: מסד נתונים 500MB, אחסון קבצים 1GB, 50,000 משתמשים פעילים בחודש, 500,000 הרצות של פונקציות שרת בחודש, עד 200 חיבורי זמן אמת בו-זמנית, **בלי גיבוי אוטומטי**, ופרויקט שלא היה בו שימוש שבוע מושהה.
- שירות המיילים המובנה של Supabase מיועד לבדיקות בלבד ושולח רק לחברי צוות הפרויקט (אומת בתיעוד הרשמי), ולכן אף תהליך לא נשען על מיילים.
- הריפו ציבורי (אומת), ולכן אסור שיופיע בו סוד כלשהו.

## 5. ארכיטקטורה

```
  Web / PWA          Android (APK)        Windows (installer)
  (browser)          Capacitor            Electron
      \                  |                    /
       \                 |                   /
        +--------- one codebase: src/ -------+
                 (Vite + React + TypeScript)
                          |
              supabase-js (HTTPS + WebSocket)
                          |
        +--------------------------------------------+
        | Supabase project (Frankfurt)               |
        |  Postgres + RLS | Auth | Realtime | Storage |
        |  Edge Function: admin-users                |
        +--------------------------------------------+
```

- **קוד אחד** ב-`src/`: React 19 ו-TypeScript, ניתוב מבוסס hash (`#/tasks`) ו-`base: './'`, כך שאותה בנייה רצה באתר, ב-WebView של אנדרואיד ובחלון Electron.
- **הקליינט מדבר ישירות עם Supabase.** האבטחה נאכפת בשרת (RLS), לא בקליינט.
- **ערכי חיבור:** כתובת הפרויקט ו-`anon key` ציבוריים מטבעם ונשמרים ב-`.env.production` בריפו. מפתח `service_role` וכל מפתח אחר לא נכנסים לריפו לעולם. הפונקציה `admin-users` מקבלת את `service_role` מ-Supabase אוטומטית כמשתנה סביבה של הפונקציה.
- **ספריות עיקריות:** react-router (HashRouter), zustand (מצב), @supabase/supabase-js, idb-keyval (תור שינויים), vite-plugin-pwa, תוספי Capacitor (local-notifications, camera, browser, app, network, filesystem, share), electron-updater. הפונטים (IBM Plex Sans Hebrew, Secular One) נארזים מקומית ולא נטענים מ-Google.
- **עיצוב ויזואלי:** ממשיך את השפה הקיימת (צבעים, טיפוגרפיה, מצב כהה) ב-CSS רגיל עם משתנים.
- **גרסאות:** מדויקות ייקבעו בתוכנית העבודה לפי תאימות. במועד הכתיבה הגרסאות האחרונות ב-npm הן Vite 8, React 19, Capacitor 8, Electron 44, supabase-js 2, Vitest 5. אם גרסה ראשית חדשה מאוד (למשל TypeScript 7) חוסמת, משתמשים בקודמת.

| יעד | טכנולוגיה | תוצר |
|---|---|---|
| אתר | Vite build, GitHub Pages, PWA להתקנה מהדפדפן | `dist/` |

- **Windows לא חתום:** SmartScreen יציג "Windows protected your PC" (More info ואז Run anyway). חתימה בתשלום מחוץ להיקף.
- **עדכונים:** Windows מתעדכן אוטומטית מ-GitHub Releases. אנדרואיד בודק מול ה-Release האחרון ומציג באנר "גרסה חדשה זמינה" עם קישור להורדה. האתר מתעדכן בטעינה מחדש.
- **חיתוך (cutover):** הפיתוח נעשה בענף `feat/platform-core`. האתר החי ממשיך להציג את האפליקציה הישנה עד שהבעלים מאשר. בחיתוך, `index.html` הישן עובר ל-`public/legacy/index.html` ונשאר נגיש ב-`/legacy/`, ו-`pages.yml` מחליף את `static.yml` (שמפרסם היום את כל הריפו). עד אז האתר החדש נבדק מקומית ובאמצעות ה-APK והמתקין.

## 7. מודל נתונים

כל הטבלאות בסכמת `public`, עם RLS פעיל. זמנים מאוחסנים כ-`timestamptz`. מחרוזות ריקות הן ברירת המחדל (לא NULL).

**`profiles`** (שורה לכל משתמש התחברות): `id` (= `auth.users.id`), `email`, `display_name` (ייחודי, ללא הבחנה בין אותיות גדולות וקטנות), `role` (`admin` או `employee`), `is_active` (ברירת מחדל true), `must_change_password`, `default_remind_min` (ברירת מחדל 15), `created_at`.

**`statuses`**: `key` (PK, לא ניתן לשינוי), `name_he`, `color`, `sort`, `is_active`. מוזרעים 17 הסטטוסים הקיימים באפליקציה, עם אותם שמות וצבעים כפי שהם מוגדרים במערך `STATUSES` ב-`index.html` הישן: processing, pending, completed, on-hold, cancelled, refunded, failed, cargo, late, bank, to-branch, await-pickup, courier, delivered-branch, pull, manager, abroad. סטטוס לא נמחק אלא מושבת, ומשימות קיימות שומרות אותו.

**`tasks`**:

| קבוצה | עמודות |
|---|---|
| זהות | `id uuid` (נוצר בקליינט), `kind` (`general` / `delivery` / `pickup`, ברירת מחדל `general`), `created_by`, `created_at`, `updated_at`, `deleted_at` |
| המשימה | `title` (חובה), `notes`, `priority` (`normal` / `high` / `urgent`, ברירת מחדל `normal`), `status_key` (ברירת מחדל `processing`), `assignee_id` (null = ללא שיוך), `due_at` (null = ללא מועד), `duration_min` (30), `remind_min` (null = ללא), `done_at` (null = פתוחה), `done_by` |
| לקוח והתקשרות | `customer_name`, `customer_phone`, `customer_phone_digits` (עמודה מחושבת: ספרות בלבד, לחיפוש), `order_number`, `service_call_number`, `glassix_conversation_id`, `no_glassix` |
| משלוח (`delivery`) | `cargo_number`, `sent_to_cargo` |
| איסוף (`pickup`) | `product_name`, `product_sku`, `thumb_attachment_id` (nullable, `on delete set null`) |
| פרטי הזמנה | `ship_method`, `ship_status`, `order_date` (טקסט כפי שמיובא), `billing`, `ship_to` |
| מורשת | `legacy_id` (ייחודי, מזהה המשימה באפליקציה הישנה), `legacy_handler` |

אילוץ במסד הנתונים: `no_glassix OR glassix_conversation_id <> ''`. משימות מיובאות מהאפליקציה הישנה נכנסות עם `no_glassix = true`. אינדקסים: `assignee_id`, `due_at` (חלקי: רק פתוחות ולא מחוקות), `order_number`, `updated_at`.

**`attachments`**: `id`, `task_id`, `storage_path`, `thumb_path`, `kind` (`image` / `screenshot` / `product`), `width`, `height`, `bytes`, `uploaded_by`, `created_at`.

**`task_events`** (יומן ביקורת): `id`, `task_id`, `actor_id`, `type` (`created`, `updated`, `status`, `assigned`, `done`, `reopened`, `deleted`, `restored`, `attachment_added`, `attachment_removed`), `changes jsonb` (`{שדה: [ישן, חדש]}`), `at`.

**`app_settings`**: `key`, `value jsonb`. מפתחות: `glassix_url_template` (טקסט עם `{id}`), `ship_methods` (מערך; ברירת מחדל: איסוף עצמי, משלוח עד הבית, נקודת איסוף, CARGO), `last_backup_at`.

**טריגרים** (רצים בשרת ולא ניתנים לעקיפה מהאפליקציה):
- `touch_task`: מעדכן `updated_at`; מונע שינוי של `id`, `created_by`, `created_at`; קובע `done_by = auth.uid()` כשמסמנים ביצוע ומאפס אותו בפתיחה מחדש.
- `log_task_event`: רושם ב-`task_events` את סוג השינוי ואת השדות ששונו, עם `actor_id = auth.uid()`. טריגר דומה על `attachments` רושם הוספה והסרה.
- `handle_new_user`: על משתמש חדש ב-`auth.users` יוצר שורת `profiles`. המשתמש הראשון במערכת הופך ל-`admin` בלי חובת החלפת סיסמה. כל השאר מקבלים את התפקיד מ-`app_metadata` (ברירת מחדל `employee`) ו-`must_change_password = true`.

**ולידציה בקליינט לפני שמירה:**
- כותרת חובה. אם היא ריקה, ממלאים "טיפול בהזמנה #X" או "לחזור אל <שם>" כמו באפליקציה הישנה.
- לפחות אחד מהשדות: מספר הזמנה, מספר קריאת שירות, שם לקוח, טלפון.
- שעה בלי תאריך אינה חוקית.
- מזהה Glassix, או סימון "אין שיחה ב-Glassix".
- בסוג `pickup` חובה שם מוצר. מק"ט מומלץ ואינו חובה.

## 8. אבטחה והרשאות

פונקציות עזר `is_member()` ו-`is_admin()` (SECURITY DEFINER, `search_path` ריק) בודקות שורת `profiles` פעילה של `auth.uid()`. כל המדיניות מוגדרת לתפקיד `authenticated` בלבד, ולתפקיד `anon` אין גישה לשום טבלה.

| טבלה | קריאה | הוספה | עדכון | מחיקה |
|---|---|---|---|---|
| `tasks` | חברים פעילים | חבר פעיל, עם `created_by = auth.uid()` | חברים פעילים | אין (מחיקה רכה באמצעות `deleted_at`) |
| `attachments` | חברים פעילים | חבר פעיל | אין | מי שהעלה, או מנהל |
| `task_events` | חברים פעילים | אין (טריגר בלבד) | אין | אין |
| `profiles` | חברים פעילים | אין (טריגר בלבד) | פונקציות `update_my_profile` (שם, תזכורת) ו-`clear_must_change_password` | אין |
| `statuses`, `app_settings` | חברים פעילים | מנהל | מנהל | מנהל |
| Storage `task-files` (פרטי) | חברים פעילים | חברים פעילים | אין | מי שהעלה, או מנהל |

- **הרשמה עצמית כבויה** בהגדרות Supabase Auth, ואורך סיסמה מינימלי מוגדר ל-10. בנוסף, גם אם נוצר משתמש, בלי שורת `profiles` פעילה ה-RLS חוסם הכול.
- **הפונקציה `admin-users`** (Edge Function) בודקת שהקורא מנהל פעיל ואז מבצעת: `create` (סיסמה זמנית אקראית, מוצגת פעם אחת), `reset_password`, `set_active` (חסימה או שחרור, וניתוק מכל המכשירים), `set_role`, `rename`. אי אפשר להשבית או להוריד מדרגה את המנהל הפעיל האחרון.
- **מחיקת משימה** היא רכה ונרשמת בהיסטוריה. כל חבר פעיל רואה גם שורות מחוקות ב-API (הקליינט מסתיר אותן), כדי שאירועי זמן אמת של מחיקה יגיעו לכולם. מנהל רואה רשימת "נמחקו לאחרונה" (30 יום) ויכול לשחזר.
- **קישורי Glassix** נפתחים רק אם תבנית הכתובת מתחילה ב-`https://`.
- **Electron:** `contextIsolation` פעיל, `nodeIntegration` כבוי, CSP שמגביל חיבורים לפרויקט Supabase, וקישורים חיצוניים נפתחים בדפדפן המערכת.
- **פרטיות:** פרטי לקוחות (שם, טלפון, כתובת) נשמרים בענן. מומלץ אזור Frankfurt. אימיילים של עובדים גלויים לכל חברי הצוות הפעילים. ההתאמה לחוק הגנת הפרטיות לא נבדקה במסמך זה.

## 9. התחברות וניהול משתמשים

- **הקמה ראשונית (פעם אחת, על ידי הבעלים):** יצירת הפרויקט, כיבוי הרשמה עצמית, הרצת קבצי ה-SQL מ-`supabase/migrations/`, ויצירת המשתמש הראשון בלוח הבקרה של Supabase (Authentication → Users). הוא הופך אוטומטית למנהל.
- **כניסה:** אימייל וסיסמה (`signInWithPassword`). ההפעלה נשמרת במכשיר ומתחדשת אוטומטית. שגיאות בעברית: סיסמה שגויה, משתמש מושבת, אין חיבור.
- **עובד חדש:** ניהול > עובדים > "עובד חדש" (שם, אימייל, תפקיד). המסך מציג סיסמה זמנית פעם אחת עם כפתור העתקה. בכניסה הראשונה העובד חייב לבחור סיסמה חדשה (לפחות 10 תווים).
- **איפוס סיסמה:** המנהל מייצר סיסמה זמנית חדשה, והעובד מנותק מכל המכשירים.
- **השבתה:** `is_active = false`. הבקשות הבאות נחסמות ב-RLS מיד, ו-`admin-users` מנתק את ההפעלות הקיימות.

## 10. זמן אמת ושינויים בזמן ניתוק

- **טעינה ראשונית:** כל המשימות הפתוחות והמשימות שבוצעו ב-30 הימים האחרונים. "חפש בכל המשימות" מריץ חיפוש בשרת (`ilike`) על כותרת, שם, טלפון בספרות בלבד, מספר הזמנה, קריאת שירות, מזהה Glassix, מספר Cargo ומק"ט.
- **זמן אמת:** מנוי Supabase Realtime על `tasks` (ובהתאמה על `profiles`, `statuses`, `app_settings`). עדכון נכנס ממוזג לפי `id`, ושינויים ממתינים מקומיים מוחלים מעל הגרסה שהגיעה מהשרת.
- **שינויים יוצאים:** מזהה המשימה נוצר בקליינט, כך ששליחה חוזרת בטוחה (upsert). שינוי נכתב קודם לתור מקומי (IndexedDB) ומשם נשלח. בכישלון רשת הוא נשאר בתור ונשלח מחדש כשהחיבור חוזר או כשהאפליקציה חוזרת למוקד. מוצג חיווי "N שינויים ממתינים".
- **התנגשות:** עדכונים חלקיים (רק השדות ששונו), והאחרון גובר. היסטוריית המשימה מראה מי שינה מה.
- **מחוץ להיקף:** עבודה מלאה ללא אינטרנט מההתחלה (בלי טעינה קודמת), ופתרון התנגשויות מתקדם.

## 12. תמונות

- **בצד הלקוח:** הקטנה לצלע ארוכה של עד 1600px ו-JPEG באיכות 0.82, ותמונה ממוזערת של 320px. קלט עד 15MB.
- **אחסון:** bucket פרטי `task-files`, בנתיבים `{task_id}/{uuid}.jpg` ו-`{task_id}/{uuid}_t.jpg`. התצוגה דרך כתובות חתומות (שעה אחת) שנשמרות בזיכרון.
- **תמונת איסוף:** תמונה מסוג `product` מוגדרת כ-`thumb_attachment_id` של המשימה.
- **מחיקה:** מוחקים את שורת `attachments` ואז מנסים להסיר את הקבצים מה-Storage. קבצים יתומים לא פוגעים, וניקוי שלהם נדחה.
- **תקציב:** כ-250KB לתמונה, כלומר כ-4,000 תמונות ב-1GB החינמי. המעקב אחר הניצול ידני בלוח הבקרה, ומדיניות שמירה תיבחן בחלק 3.

## 13. תזכורות והתראות

- משימה של העובד המחובר עם `due_at` ו-`remind_min` מייצרת התראה מקומית. מתוזמנות ההתראות של 48 השעות הקרובות (עד 60), ומתוזמנות מחדש בכל שינוי נתונים ובכל פתיחה.
- **אנדרואיד:** Capacitor Local Notifications, עם בקשת הרשאת התראות (אנדרואיד 13 ומעלה) והרשאת התראות מדויקות. בלי ההרשאה ההתראה מגיעה בקירוב.
- **Windows:** Electron. סגירת החלון משאירה את האפליקציה פעילה במגש המערכת, ויציאה מלאה מתבצעת מתפריט המגש.
- **אתר:** Notification API כשהדף פתוח.
- **מגבלה ידועה:** אם האפליקציה לא רצה ומשימה הוקצתה למכשיר אחר, ההתראה תגיע רק כשהמכשיר יסתנכרן. התראות דחיפה אמיתיות (FCM) הן חלק 3.

## 14. ייבוא וגיבוי

- **ייבוא מגיבוי ישן:** קובץ CSV מהכפתור "הורד קובץ גיבוי" באפליקציה הישנה, או הורדה כ-CSV מגיליון Google של הצוות (יש לו אותה פריסה). 22 העמודות (מזהה, משימה, מועד טיפול, משך, תזכורת, דחוף, בוצע, בוצע בתאריך, הערות, הזמנה, שם, טלפון, מצב, בטיפול של, Shipping Method, סטטוס משלוח, CARGO, תאריך הזמנה, חיוב, שלח אל, נוצר, עודכן) ממופות לשדות החדשים; העמודה CARGO ממופה ל-`sent_to_cargo`. המזהה הישן נשמר ב-`legacy_id` ומונע כפילות בייבוא חוזר. אם מזהה מופיע כמה פעמים (כמו בגיליון), נלקחת השורה האחרונה, ושורות שסומנו "נמחק" מדולגות. "בטיפול של" מותאם לעובד לפי `display_name` זהה, ומי שלא נמצא נשמר ב-`legacy_handler` ומוצג כתווית עד ששויך ידנית. כל המשימות המיובאות מסומנות `no_glassix`.
- **ייבוא הזמנות מ-CSV (כמו היום):** זיהוי עמודות לפי כותרות (הזמנה, שם, טלפון, מצב, סטטוס משלוח, Shipping Method, בטיפול של, חיוב, שלח אל, תאריך), דילוג על מספרי הזמנה קיימים, ועד 300 בכל פעם.
- **גיבוי:** כפתור מנהל "הורד גיבוי" יוצר CSV של כל המשימות (כולל שבוצעו ונמחקו) באותה פריסה, ומעדכן `last_backup_at`. אם עברו 7 ימים בלי גיבוי, מוצג למנהל באנר. באנדרואיד הקובץ נמסר דרך חלון השיתוף של המערכת.
