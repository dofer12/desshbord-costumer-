# M3 Admin Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (the author executes this plan inline; the owner waived per-stage approval on 2026-10-15). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An administrator manages the team and the data of the app from the app itself: creates employees, resets and blocks them, edits the statuses and the settings, imports orders and the old backup, downloads a backup and restores deleted tasks. Every person chooses their own password on the first sign-in and edits their own profile.

**Architecture:** Two pieces of server code and a set of screens. (1) `supabase/migrations/0003_admin.sql`: a trigger that keeps the last active administrator from being blocked or demoted by anybody, and a function that ends all the sessions of a user. (2) The Edge Function `admin-users`, the only code that holds the secret key: its rules are a pure module (`logic.ts`) that is tested against the real SQL in PGlite, behind a thin HTTP layer (`handler.ts`) and a Deno entry (`index.ts`). The app reaches both through an `AdminGateway` that is part of the `Backend` (Supabase in the app, memory in the tests and the demo). The screens live in `src/features/admin/`; CSV reading and writing, the old file formats and the matching of statuses and people are pure modules with their own tests. A small `FileSaver` hides how a file is handed to the person (a download in a browser and in Windows, the share sheet on Android).

**Tech Stack:** The M2 stack, plus `@capacitor/share` and `@capacitor/filesystem` (8.x) for the backup on Android, and `npm:@supabase/supabase-js@2` inside the Deno function. No CSV library: the old app's parser is small and its behaviour is the specification.

**Spec:** `docs/superpowers/specs/2026-10-13-platform-core-design.md`, sections 7 (`profiles`, `statuses`, `app_settings`), 8 (the `admin-users` function and the table of permissions), 9 (users), 11 (Admin, Profile, the first-password screen), 14 (import and backup), 15 (tests) and the M3 row of section 16. The behaviour to match for import and backup is that of `public/legacy/index.html` (`parseCSV`, `mapHeaders`, `matchStatus`, `parseDue`, `buildImport`, `BK_COLS`, `tasksToCSV`, `csvToTasks`, `restoreFromFile`, `downloadBackup`).

**How this plan is used:** the author is also the executor, and the owner asked for M1 to M4 to be built without approval between stages. So the plan is a resumable list of tasks with interfaces, rules and test cases; code is written test-first in the repository and committed per task. The ledger is `.superpowers/sdd/2026-10-17-m3-admin/progress.md`. **Three steps belong to the owner and cannot be done from here:** pasting `0003_admin.sql` in the Supabase SQL Editor, deploying the function (`npx supabase login` opens a browser and the owner approves), and trying everything on the real devices. The plan prepares each of them (a guide, a script, a check that says what is wrong) and goes on.

## Global Constraints

- **Language and layout:** as M2. UI strings in Hebrew, right to left; identifiers and logs in English; the column names of a CSV file are Hebrew, as in the old app (the two that the old app already has in English, `Shipping Method` and `CARGO`, stay so); numbers, times and hostnames use the `.num` class.
- **Who may do what (spec section 8):** the Admin tab and every `/admin/...` route are for `role === 'admin'` only (the others are sent to Today), but the screens are never the protection: RLS (`statuses`, `app_settings`, tasks) and the function check every write again. A request to the function is judged by the token it carries, never by anything in its body.
- **Passwords:** at least 10 characters, as the project's setting says. A temporary password is 16 random characters from an alphabet without look-alikes (no `I l O 0 1`), made from a cryptographic source with no modulo bias, returned **once** to the administrator who asked, kept in memory only for as long as the dialog that shows it is open, and never written to a log, a URL, `localStorage`, the history or an error message. The responses of the function are `Cache-Control: no-store`.
- **No secret in the repository or in the chat:** the function reads its keys from its own environment (`SUPABASE_SECRET_KEYS`, falling back to `SUPABASE_SERVICE_ROLE_KEY`); the owner's access token for the CLI is approved in the owner's browser. The live check keeps asking for the secret key in a hidden prompt, as in M1.
- **Last administrator (spec section 9):** the last active administrator can be neither blocked nor demoted nor deleted, whoever tries and by whatever route (the function, the dashboard, SQL). The function also refuses, with a plain message, an administrator who blocks or resets **themselves** (a locked-out sole administrator has no way back, because the app sends no e-mail); renaming themselves and changing their own role are allowed (the guard above protects the last one).
- **CSV (as the old app):** a backup file is UTF-8 with a byte-order mark, CRLF line ends, every cell quoted, one row per task; a file that is read may use `,`, `;` or a tab, a BOM, quotes with doubled quotes, line breaks inside a cell, and (when it is not UTF-8) Windows-1255. The first 22 columns and their Hebrew names are those of the old app (`מזהה, משימה, מועד טיפול, משך בדקות, תזכורת בדקות, דחוף, בוצע, בוצע בתאריך, הערות, הזמנה, שם, טלפון, מצב, בטיפול של, Shipping Method, סטטוס משלוח, CARGO, תאריך הזמנה, חיוב, שלח אל, נוצר, עודכן`); the 23rd is `נמחק` (as in the team sheet); the new app adds columns after them, which the old app ignores. A cell that a spreadsheet would run as a formula is written with a leading apostrophe and read back without it.
- **Import (spec section 14):** nothing is added twice: the old id (`legacy_id`) and, for orders, the order number are the keys; of an id that appears several times the **last** row counts; a row marked `נמחק` is skipped; imported tasks are `no_glassix`; local times in a file are Jerusalem time whatever the zone of the device; the import of orders takes 300 at a time. The person in "בטיפול של" is matched by `display_name` (ignoring case and spaces at the ends), and a name that matches nobody is kept in `legacy_handler`.
- **Statuses are never deleted** (spec section 7): they are blocked and tasks keep them; the key never changes.
- **Git:** as M2. Work only on `feat/platform-core` in `C:\dev\desshbord-costumer-`; commit after every task; every commit message ends with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; a push of the feature branch after the stage is allowed; a tag or a release always needs a new go-ahead; no secret enters the repository or the chat.
- **Versions:** unchanged, plus `@capacitor/share` and `@capacitor/filesystem`. The version of the app becomes 0.4.0 at the end (no tag).

## Review Focus

The failure modes a person using this software is most likely to hit (and the ones that would hurt most), each pinned by a test in the task that owns the code:

1. **The administrator function must be impossible to misuse:** an employee, a blocked administrator, a caller with no token or a forged or expired one, a body that claims another caller or another role, an oversized or malformed body, an unknown action, a user id that is not a UUID or does not exist: each is refused with the right status and changes nothing. The last active administrator cannot be blocked, demoted or deleted, not even by two administrators acting at the same moment or from the dashboard; an administrator cannot block or reset themselves. Pinned in Tasks 1 to 3.
2. **A temporary password is shown once and goes nowhere else; a reset or a block really disconnects the person; the first password is chosen before anything else:** the password is absent from every log line, error and storage; reset and block end every session; a person with `must_change_password` cannot reach any screen until they choose a new password (also when the flag is set while the app is open), and cannot choose the temporary one again. Pinned in Tasks 2, 3, 5 and 6.
3. **Import without duplicates and without loss:** the same file twice adds nothing; the last of several rows with one id wins; a deleted row is skipped; a status, a person, a date, a number of minutes or a boolean that cannot be read falls back as documented and is reported, never crashes; a date keeps its day in Jerusalem (a task at 00:30 stays on its day); a file that is not UTF-8, has a BOM, uses `;` or a tab, has quotes and line breaks inside cells, trailing empty columns, Windows line ends or no final line end reads the same; an enormous or empty or wrong file is refused with a plain message. Pinned in Tasks 9 and 10.
4. **A backup that can be restored:** export then import gives back every field of every task (Hebrew, quotes, commas, line breaks, long notes), with the new columns; a cell that starts with `=`, `+`, `-` or `@` cannot run as a formula in a spreadsheet and still comes back unchanged; 10,000 tasks are exported in pages without freezing the screen; `last_backup_at` is written only after the file has been handed to the person; the banner appears after seven days, for administrators only, and not for an installation with no tasks. Pinned in Tasks 9 and 11.
5. **The admin screens under failure and concurrency:** two administrators editing the same status or setting; a status in use is blocked and not removed, keeps its key and its place; a Glassix template that is not `https://` or has no `{id}` is refused; the list of shipping methods keeps at least one entry and no duplicates; "recently deleted" shows the last 30 days only, and a restored task comes back to everybody; every action that fails says so in Hebrew and leaves the screen usable; a function that is not deployed gives a message that says what to do. Pinned in Tasks 4, 6, 7, 8 and 12.

## Not in M3

Dark mode, the PWA, the content security policy, the app icon, the accessibility and performance polish (M4); pictures and history in the backup file and the automatic backup (part 3); inviting a person by e-mail and recovering a password by e-mail (the app sends none); deleting a user (a person who created tasks cannot be deleted by the schema: they are blocked); several organisations; a new design for the statuses.

### Task 1: The administrator guard and the end of sessions (SQL)

**Interfaces:**

- Produces: trigger `profiles_protect_last_admin` (before update of `role`, `is_active` and before delete on `public.profiles`) that raises `profiles_last_admin` (SQLSTATE `23514`) when the change would leave no active administrator, after taking `pg_advisory_xact_lock` so that two such changes made at the same moment are judged one after the other; `public.revoke_user_sessions(p_user_id uuid) returns void` (security definer, empty `search_path`, deletes the rows of `auth.sessions` of that user; executable by `service_role` only).

- [ ] **Step 1: Write the failing tests** (`0003_admin.test.ts`, on the PGlite world that runs 0001 to 0003):
  - the only active administrator cannot be blocked, demoted to employee or deleted (three tests, each `rejects.toThrow(/profiles_last_admin/)` and the row unchanged);
  - with a second active administrator, one of them can be demoted, and then the other (now the only one) cannot;
  - a blocked administrator does not count: with one active and one blocked administrator the active one cannot be demoted; un-blocking the second first makes it possible;
  - changes that do not touch `role` or `is_active` (display name, `must_change_password`, `default_remind_min`) of the last administrator are allowed;
  - employees can be blocked, promoted, renamed and deleted freely; promoting an employee and blocking the old administrator in that order is allowed;
  - the guard holds for the superuser (RLS is bypassed, the trigger is not);
  - `revoke_user_sessions` removes the sessions of the user it is given and leaves another user's; it is not executable by `anon` or `authenticated` (`has_function_privilege` is false) and is by `service_role`; with an unknown id it removes nothing and does not fail;
  - the SQL text takes `pg_advisory_xact_lock` before it counts (a comment says that PGlite has one connection, so two parallel callers cannot be tried here).

### Task 2: The rules of the `admin-users` function

**Files:**
- Create: `supabase/functions/admin-users/logic.ts`, `supabase/tests/adminUsers.logic.test.ts`, `supabase/tests/adminUsers.db.test.ts`

**Interfaces:**
- Consumes: Task 1 (the guard raises `profiles_last_admin`); `Role` and the profile columns of `src/features/auth/types.ts` (re-declared in `logic.ts` so that the function has no import from `src/`).
- Produces (no Deno or Node API is used; randomness comes in through `deps`):
  - `type AdminRequest = { action: 'create'; email: string; display_name: string; role: Role } | { action: 'reset_password'; user_id: string } | { action: 'set_active'; user_id: string; is_active: boolean } | { action: 'set_role'; user_id: string; role: Role } | { action: 'rename'; user_id: string; display_name: string }`
  - `type AdminErrorCode = 'unauthenticated' | 'forbidden' | 'invalid' | 'email_taken' | 'name_taken' | 'not_found' | 'last_admin' | 'failed'`
  - `type AdminResult = { ok: true; user: ProfileRow; temp_password?: string } | { ok: false; code: AdminErrorCode; field?: string }` (`temp_password` only for `create` and `reset_password`)
  - `interface AdminDeps { identify(token: string): Promise<string | null>; profile(id: string): Promise<ProfileRow | null>; profileByName(name: string): Promise<ProfileRow | null>; profileByEmail(email: string): Promise<ProfileRow | null>; authCreate(input: { email: string; password: string; role: Role; display_name: string }): Promise<{ id: string } | { error: 'email_taken' | 'failed' }>; authSetPassword(id: string, password: string): Promise<boolean>; authBan(id: string, banned: boolean): Promise<boolean>; authDelete(id: string): Promise<void>; revokeSessions(id: string): Promise<boolean>; updateProfile(id: string, patch: Partial<Pick<ProfileRow, 'role' | 'is_active' | 'display_name' | 'must_change_password'>>): Promise<ProfileRow | { error: 'name_taken' | 'last_admin' | 'not_found' | 'failed' }>; randomBytes(n: number): Uint8Array; log(line: Record<string, unknown>): void }`
  - `handleAdminRequest(deps: AdminDeps, token: string | null, body: unknown): Promise<AdminResult>`
  - `makeTempPassword(randomBytes: (n: number) => Uint8Array): string`, `parseAdminRequest(body: unknown): AdminRequest | { invalid: string }`

- [ ] **Step 1: Write the failing tests.** Unit tests with fake deps (`adminUsers.logic.test.ts`):
  - **Who is calling:** no token or an empty one is `unauthenticated` and `identify` is not even asked; a token `identify` does not know is `unauthenticated`; a known user with no profile, with an employee profile or with a blocked administrator profile is `forbidden`; **nothing in the body** (`caller_id`, `role: 'admin'`, `is_admin: true`, `app_metadata`) changes who the caller is. In every one of these cases no `auth*`, `updateProfile` or `revokeSessions` is called.
  - **Validation (`invalid`, with the `field`):** unknown or missing `action`; `create` with an e-mail that is empty, has no `@`, has spaces, or is over 254 characters; a display name that is empty after trimming, over 60 characters or has control characters; a role other than `admin` or `employee`; a `user_id` that is not a UUID; `is_active` that is not a boolean; extra unknown fields are ignored; the e-mail is lower-cased and trimmed, the name trimmed; non-object bodies (`null`, an array, a string) are `invalid`.
  - **`create`:** a name or an e-mail that already exists is `name_taken` / `email_taken` *before* any user is created (`profileByName`, `profileByEmail`, compared without regard to case); `authCreate` is given the role and the name; the result carries the profile and a 16-character temp password; an `authCreate` error `email_taken` maps to `email_taken` and any other to `failed`; if the profile cannot be read after the user was created, the user is deleted (`authDelete`) and the result is `failed` with no orphan.
  - **`reset_password`:** sets a new temp password, sets `must_change_password` true, ends the sessions, and returns the temp password once; an unknown user is `not_found`; **the caller resetting themselves is `invalid` with `field: 'user_id'`** (use the profile page); a failure of `authSetPassword` is `failed` and the flag is not set.
  - **`set_active`:** blocking sets `is_active` false *first* (so that RLS stops the person at once), then bans and ends the sessions; unblocking lifts the ban; **the caller blocking themselves is `invalid`**; `updateProfile`'s `last_admin` is passed on as `last_admin` and nothing else is done; a failing ban or revoke after the profile was changed is `failed` (the call is safe to repeat).
  - **`set_role`:** changes the role; `last_admin` passes on; setting the role a user already has is a success that changes nothing.
  - **`rename`:** trims; `name_taken` passes on (also when only the case differs); renaming to the same name succeeds.
  - **No password anywhere:** for every action and every outcome, the `log` lines and the error results contain neither a temp password nor the token (assert by searching the serialised calls); a log line has the caller id, the action, the target id and the code.
  - **`makeTempPassword`:** 16 characters, all from the alphabet (no `I l O 0 1`), different on every call with different bytes, deterministic for given bytes; **no modulo bias** (bytes at or above 224 are skipped: feed `[255, 224, 0, 1…]` and check which characters come out); it asks for more bytes when many are rejected, and does not loop forever on an all-rejected source (it gives up with an error after a fixed number of rounds).
  - **Against the real SQL** (`adminUsers.db.test.ts`): the same `handleAdminRequest` with `AdminDeps` written over the PGlite world (`authCreate` inserts into `auth.users` with the role in `raw_app_meta_data` and the name in `raw_user_meta_data`, so the **real `handle_new_user` trigger** makes the profile; `updateProfile` is an `update public.profiles`, so the **real guard** answers; `revokeSessions` calls the real `public.revoke_user_sessions`): `create` makes an active profile with `must_change_password` true and the right role; a second `create` with the same name in another case is `name_taken`; blocking the only administrator is `last_admin` and the row is unchanged; with two administrators the first can be blocked and the second then cannot; `reset_password` leaves the flag true and the user's `auth.sessions` empty; blocking removes the sessions.
- [ ] **Step 2: Run, see them fail.**
- [ ] **Step 3: Implement** `logic.ts` (order of operations as the tests say; `makeTempPassword` with rejection sampling over `56` characters; errors are values, nothing throws for an expected case; an unexpected throw inside is caught at the top and becomes `failed`).
- [ ] **Step 4: Run both files and the whole `supabase` folder, typecheck, lint.**
- [ ] **Step 5: Commit** `feat: add the rules of the administrator function`.
