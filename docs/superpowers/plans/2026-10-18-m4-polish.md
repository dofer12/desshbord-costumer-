# M4: polish and version 1.0 Implementation Plan

> **Note on how it is built:** the owner told the executor (2026-10-17, three times) to go on to the end **without tests**. This plan is therefore a task list with decisions and no test steps: nothing here is written test-first, no mutation check is run, and CI after a push is the first full check. The ledger says which tasks were built that way. If the owner asks for tests again, the first thing to write is the list under "What to test when tests are back".

**Goal:** the last stage of part 1: the things that make the app finished to use (a theme the person chooses, an icon, an installable web app, a policy that limits what the pages may connect to, a check for a newer version, keyboard and screen-reader polish, and a smooth list of 2,000 tasks), and the guide and the version for 1.0.

**Spec:** `docs/superpowers/specs/2026-10-13-platform-core-design.md`, section 11 (the profile: "מצב כהה / בהיר / אוטומטי, ... גרסה ובדיקת עדכון"; "מצבים") and section 16 (M4: error, empty and offline states; accessibility; performance; dark mode; CSP for the site and the Windows app; app icon; PWA).

**Not done here, because they are the owner's:** the tag and the release `v1.0.0`, and the publishing of the new site (the cutover of GitHub Pages and the merge into `main`) each need the owner's fresh go-ahead; the manual acceptance on the phone and the laptop is theirs too.

## Global constraints

- Hebrew, right to left; the nouns and plural imperatives of the other screens.
- No secret in the repo; the Supabase URL and the publishable key are public and already in `.env`.
- A change must not break the three targets: the web (a server), the Android WebView (`https://localhost`) and the Windows app (`file://`).
- The demo (`--mode demo`) stays out of every other build.

## Tasks

1. **Theme.** `src/lib/theme.ts` (read, apply and keep the choice of this device: automatic, light or dark; `data-theme` on the root element, which `tokens.css` already understands; the colour of the browser bar follows). It is applied before the first render. The profile gets a choice "מראה".
2. **App icon.** One drawing (`build/icon.svg`) in the colour of the app, turned into the files of every target by a script that uses the Electron that is already installed: the Windows icon (`build/icon.png`, which electron-builder turns into the `.ico`), the tray icon, the launcher icons of Android (all densities, the round ones and the adaptive foreground), the icons of the web app and the favicon.
3. **Installable web app (PWA).** A manifest, the icons, `theme-color`, the Apple touch icon, and a small service worker that keeps the shell (the page and the hashed files) so that the app opens fast and shows its offline message when there is no network, and never keeps anything of the server. It is registered only in a web build served over https, never in the Android app, the Windows app, the demo or development.
4. **Content-Security-Policy.** A policy written into the page of every build (not development), made from the address of the project: scripts only from the page itself, connections only to the project (https and the live connection) and to the place where releases are listed, pictures from the page, from the project, and from data and blob, no objects, no frames, and a base and a form that stay on the page.
5. **Version and update check.** The profile shows the version and a button that asks the list of releases whether there is a newer one, and says so with a link to the page of the releases. The answer is never trusted beyond a version number.
6. **Keyboard and screen reader.** A link that skips to the page, the focus moving to the page when the tab changes, and the motion that the person turned off in their device being off.
7. **A list of 2,000 tasks.** The changes that arrive live are applied together and not one by one (an import of 300 tasks is 300 events), and the heavy selections are looked at.
8. **The guide and the version.** `docs/setup-he.md`: a section for 1.0 (the theme, the icon, installing as a web app, the update check) and the full manual acceptance list that joins the lists of 0.1 to 0.4; `README.md`; version 1.0.0 in `package.json` (no tag).

## What to test when tests are back

The theme (the choice is kept, applied before the first render, and the browser bar follows); the policy (a build has it, development does not, and it names only the project that the build was made for); the service worker (it never answers a request of another origin, a page is fetched from the network first); the update check (a newer version, the same, an older one, an answer that is not a version, a network that fails); the batching of the live changes (the same final state as one by one, in order, with the last row of an id winning); the icons (the files exist, with the sizes that each target asks for); a list of 2,000 tasks (the first page renders in the time of a frame budget).
