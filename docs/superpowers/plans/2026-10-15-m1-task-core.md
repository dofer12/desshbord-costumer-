# M1 Task Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (the author executes this plan inline; the owner waived per-stage approval on 2026-10-15). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tasks that live in Supabase and appear on every device within seconds: schema with row level security, a task table and a task card with all three kinds, images, a tamper-proof history, and a queue that never loses or duplicates a save.

**Architecture:** Everything the client does with Supabase goes through small gateway interfaces (`TasksGateway`, `DirectoryGateway`, `AttachmentsGateway`), as the auth store already does, so every behaviour is unit-tested against a fake and a few contract tests run the real supabase-js client against a stubbed network. Writes go through an outbox (a queue in IndexedDB) and are idempotent upserts with client-generated ids; incoming realtime rows are merged by id with still-pending local patches applied on top. The schema, triggers and policies are one migration, `0002_core.sql`, tested in a real Postgres (PGlite).

**Tech Stack:** The M0 stack (Vite 8, React 19, TypeScript ~6.0, zustand 5, supabase-js 2, Vitest 5 with Testing Library, PGlite) plus `idb-keyval` for the outbox. No UI library: plain CSS with the existing tokens.

**Spec:** `docs/superpowers/specs/2026-10-13-platform-core-design.md`, sections 7, 8, 10, 11 (tasks screen and task card), 12 and 15, and the M1 row of section 16. Plans for M2 to M4 follow this one.

**How this plan is used:** the author is also the executor, and the owner asked for M1 to M4 to be built without approval between stages. So the plan is a resumable list of tasks with interfaces, rules and test cases; code is written test-first in the repository and committed per task. The ledger is `.superpowers/sdd/2026-10-15-m1-task-core/progress.md`.

## Global Constraints

- **Language and layout:** UI strings in Hebrew, right to left; identifiers and log text in English. Phone numbers, order numbers, versions and hostnames use the `.num` class. Email and password inputs use `dir="ltr"`.
- **Time:** zone `Asia/Jerusalem`; a date without a time means 09:00 local (the old app's rule); a time without a date is an error ("נבחרה שעה בלי תאריך. בחר גם תאריך טיפול.").
- **Database conventions (spec section 7):** all tables in `public` with RLS on; times are `timestamptz`; text columns default to `''`, never NULL; `tasks.id` is created by the client; deleting a task is soft (`deleted_at`), and nobody may `DELETE` a task row.
- **Permissions (spec section 8):** policies are for `authenticated` only and `anon` reaches no table; `tasks` read: active members, insert: an active member with `created_by = auth.uid()`, update: active members, delete: nobody; `attachments` read and insert: active members, delete: the uploader or an admin; `task_events` read: active members, no writes except by trigger; `statuses` and `app_settings` read: active members, write: admin; the triggers are `SECURITY DEFINER` with `search_path = ''`.
- **Statuses:** the 17 statuses of the old app are seeded with its names and colours (`processing` בטיפול #22a559, `pending` בהמתנה לתשלום #6b7280, `completed` הושלמו #7c9cc0, `on-hold` משהה #e9a45c, `cancelled` בוטלו #3a4250, `refunded` החזר כספי #9aa3ad, `failed` נכשלו #e0707a, `cargo` Send to CARGO #1e88c9, `late` חריגה מהצפי #f08a80, `bank` ממתינה להעברה בנקאית #2fb86a, `to-branch` הועבר לאיסוף מסניף #8fcf9b, `await-pickup` ממתין לאיסוף לקוח #a78bda, `courier` נמסר לחברת שליחויות #d4b800, `delivered-branch` נמסר ללקוח בסניף #8aa7c7, `pull` משיכה מסניפים #d93a32, `manager` טיפול מנהל #c2185b, `abroad` הזמנת חו"ל #18c13a). Shipping methods default to איסוף עצמי, משלוח עד הבית, נקודת איסוף, CARGO.
- **Data flow (spec section 10):** the first load is every open task and every task done in the last 30 days (not deleted); "search all tasks" runs on the server (`ilike`) over title, customer name, phone digits only, order number, service call number, Glassix id, Cargo number and SKU; incoming rows merge by `id`; outgoing changes are partial patches, last write wins; a change is written to the local queue first and sent from there; the screen shows "N שינויים ממתינים".
- **Images (spec section 12):** resized on the client to a long edge of at most 1600 px as JPEG quality 0.82, plus a 320 px thumbnail; input up to 15 MB; private bucket `task-files`, paths `{task_id}/{uuid}.jpg` and `{task_id}/{uuid}_t.jpg`; shown through signed URLs (one hour) kept in memory; a `product` image becomes the task's `thumb_attachment_id`.
- **Glassix:** a task needs a Glassix conversation id or the "אין שיחה ב-Glassix" tick; the "פתח שיחה" button exists only when the template setting is a valid `https://` URL containing `{id}`.
- **Screens (spec section 11):** tasks are a table on a laptop and cards on a phone, 100 rows per page, status chips with counts, default filter "המשימות שלי" with a switch to everyone.
- **Git:** work only on `feat/platform-core` in `C:\dev\desshbord-costumer-`; commit after every task; every commit message ends with the line `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; the owner allows a push of the feature branch after each stage; a tag or a release always needs a new go-ahead; no secret enters the repository or the chat.
- **Versions:** unchanged from M0. New dependency: `idb-keyval`.

## Review Focus

The failure modes a person using this software is most likely to hit, each pinned by a test in the task that owns the code:

1. **A save that fails halfway** (offline, timeout, the app closed): the task is neither lost nor duplicated. The id is created once, the resend is an idempotent upsert, and "N שינויים ממתינים" tells the truth. Pinned in Tasks 5 and 6.
2. **Two people editing the same task:** each sends only the fields they changed, so neither overwrites the other's field; a remote update arriving while the card is open does not wipe what the user has typed. Pinned in Tasks 6 and 9.
3. **A user deactivated while the app is open** must not keep a silently empty list: the app notices and returns to the login screen with an explanation. Pinned in Task 7.
4. **Phone numbers and search text:** "050-123 4567", "+972 50 123 4567" and "0501234567" find the same customer by digits, and commas, parentheses, quotes and percent signs in the search box neither break the query nor match everything. Pinned in Task 4.
5. **Glassix and images:** saving without a Glassix id and without the tick is refused; an id with spaces or slashes is URL-encoded in the link; a non-image or a file over 15 MB is refused before anything is uploaded; a failed upload leaves no row without a file and no file without a row. Pinned in Tasks 4, 5 and 10.

### Task 2: Triggers: touch, history and attachment events

**Files:**
- Modify: `supabase/migrations/0002_core.sql` (part 2: functions and triggers)
- Modify: `supabase/tests/0002_core.test.ts`

**Interfaces:**
- Produces (SQL): `public.touch_task()` (BEFORE INSERT OR UPDATE on `tasks`), `public.log_task_event()` (AFTER INSERT OR UPDATE on `tasks`), `public.log_attachment_event()` (AFTER INSERT OR DELETE on `attachments`), all `SECURITY DEFINER` with `search_path = ''`.
- Rules: on INSERT with `done_at` set and no `done_by`, `done_by` becomes `coalesce(auth.uid(), created_by)`. On UPDATE: `id`, `created_by` and `created_at` keep their old values whatever the caller sends; `updated_at = now()`; `done_by` is the caller when `done_at` goes from null to a value, null when `done_at` is null, otherwise unchanged. `log_task_event` writes `created` on insert; on update it diffs `to_jsonb(old)` and `to_jsonb(new)` ignoring `updated_at`, `done_by`, `created_at` and `customer_phone_digits`, and writes one event per category: `deleted` or `restored` for `deleted_at`, `done` or `reopened` for `done_at` (null to value, value to null), `status` for `status_key`, `assigned` for `assignee_id`, and `updated` for every other changed field, each with `changes = {field: [old, new]}` for only its own fields and `actor_id = auth.uid()`. An update that changes nothing writes nothing. The attachment trigger writes `attachment_added` and `attachment_removed` on the task with `changes = {attachment: [old, new]}`.

  - `events`: insert gives one `created` event; changing `title` and `notes` gives one `updated` event whose `changes` has exactly those two fields with old and new values; changing `status_key` gives a `status` event; changing the assignee gives `assigned`; marking done gives `done`, clearing it gives `reopened`; setting `deleted_at` gives `deleted`, clearing it `restored`; a combined update (status plus notes) gives two events; a no-op update gives none; `actor_id` is the caller; the phone digits and `updated_at` never appear in `changes`.
  - `attachments`: inserting an attachment writes `attachment_added` on its task, deleting it writes `attachment_removed`.
  - `unforgeable`: a signed-in user cannot `insert into task_events` and cannot call the trigger functions (this part is finished in Task 3 once the grants exist).
